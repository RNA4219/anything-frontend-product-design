# C-001 Round 01 — Researcher-2 independent research

## 結論

「利用不可のコントロールはすべて `disabled`」「モーダルは常に最初の Tab 対象へフォーカス」は採用しない。公式資料に明示的な例外がある。C-001 で有用なのは、**状態の意味・到達可能性・実行抑止・初期フォーカス・終了後の復旧を別々に定義した操作契約**である。

既存 Art Direction の E2-01〜06、I-09〜11 はモーダルの基本事項をすでに扱っている。追加すべき候補は、実装事故から導いた「起動元が消えても背後画面の復旧を必ず実行する」「初期フォーカスを動かす担当を一つにする」「内容全置換で Tab 対象がゼロになった場合の行先を定める」という運用条件である。以下の規則案は出典の直訳ではなく、本調査の提案として分離する。

## 事実と規則案

### 1. 利用不可状態には複数の設計がある

**確認した事実。** [GOV.UK Button の Disabled buttons](https://design-system.service.gov.uk/components/button/#disabled-buttons) は、無効ボタンを理解しにくい場合があるとして、ユーザー調査で有益だと分かる場合に限定する。これは GOV.UK の設計指針であり、HTML仕様の禁止規則ではない。[USWDS Button](https://designsystem.digital.gov/components/button/#accessibility-guidance) は理由と解除方法の説明を求め、ネイティブ `disabled` によるTab順からの除外と、`aria-disabled` による到達可能な状態通知を区別する。後者ではアプリ側が各入力手段からの実行を止める必要がある。

**提案 P1。** 利用不可状態には「理由」「利用可能になる条件」「説明への到達方法」「Tab順に残すか」「実行を止める担当」を書く。値だけを決める規則にしない。

**反例。** 入力不足で送信できない理由を知るため、ユーザーがボタンへ移動できる必要がある画面。単純な `disabled` 化で唯一の説明への経路も消す実装は、この要件を満たさない。逆に、説明が常時表示されTab順から外す判断に根拠があるなら、ネイティブ `disabled` は妥当な選択肢である。

**反証テスト。** `aria-disabled` 中にクリック・Enter・Spaceで実行されないか確認する。ポインター専用ツールチップだけが理由を提供する場合は、キーボードのみで理由と解除条件を理解できるか確認する。後者は本調査の提案テストであり、本調査で実機検証した結果ではない。

### 2. 初期フォーカスは内容と操作結果から選ぶ

**確認した事実。** [APG Dialog Modal の Keyboard Interaction / Note](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/#keyboardinteraction) は、構造のある説明や長文では静的な見出し等、取り消し困難な操作では最も破壊的でない選択肢を初期対象とする場合を示す。起動元消失時は作業の流れに沿う別の要素へ戻す。APGは実装ガイダンスであり、これをそのままWCAG達成基準と呼ばない。

**提案 P2。** コンポーネント契約に初期対象の選定理由と担当を明記する。フォーカストラップ、ライブラリ本体、アプリ側Effectの複数箇所が同時に動かさない。

**実装事故。** [USWDS PR #6703](https://github.com/uswds/uswds/pull/6703) は、トラップとモーダルが双方でフォーカスを動かし、NVDAで名前等が繰り返される問題を説明している。修正はトラップの自動移動を止め、モーダル側が移動を担当した。フッター先頭ボタンという対象は操作中心の確認モーダルに合わせた選択である。iOS Safariで初期読み上げが異なるという既知制約も記録されている。

**反例とテスト。** 長い説明の末尾ボタンを最初のTab対象にすると、導入が画面外へ移動する場合がある。破壊的ボタンがDOM順先頭でも機械的に選ばない。開いた直後のフォーカス移動回数、導入の可視性、対象ブラウザーと支援技術での名前の読み上げを確認する。「全環境で発話を厳密に一回にする」とは規則化しない。

### 3. 終了後の画面復旧を起動元の存在に依存させない

**確認した事実。** [USWDS PR #6786](https://github.com/uswds/uswds/pull/6786) は、起動元要素が消えると画面の `aria-hidden` が解除されない故障を記録する。解除処理が `if (menuButton && returnFocus)` の中にあり、起動元検索失敗でスキップされた。修正では画面の復旧を条件分岐の外へ出し、フォーカス復帰だけを条件内に残した。起動元を削除する回帰テストと修正前失敗の報告があるが、本調査では追試していない。

**提案 P3。** モーダル終了時は「背後の操作・支援技術への公開状態を復旧」と「復帰先を決めてフォーカス」の成功条件を分ける。後者の失敗で前者を省略しない。複数モーダルが残る場合は、残る最上位モーダルの制限を維持する必要がある。このスタック例外は提案であり、当該PRがその全ケースを保証したという意味ではない。

**具体的な反証。** 一覧行の削除確認を開く→行の再描画で起動元を削除→閉じるボタンとEscapeを別々に試す。画面は見えているのに読み上げ対象から消えたまま、残留 `inert` / `aria-hidden` がある、または予定した復帰先がない場合は契約違反。元々必要だった非公開属性をすべて無差別に消すテストにはしない。

### 4. Tab対象がゼロでもフォーカス可能な対象はあり得る

**確認した事実。** [Adobe PR #2763](https://github.com/adobe/react-spectrum/pull/2763) は、ダイアログ内容変更後にTab移動可能な要素がなくなるケースで、フォーカス可能な要素へ戻す修正を示す。テスト手順は内容を順番に置き換え、最後にTab対象のない画面へ進む。これは初期フォーカスとは別の「動的更新後の保全」の問題である。

**提案 P4。** 読み込み中・処理結果などで子要素を全置換するモーダルは、現在のフォーカス消失時の行先を定める。フォーカス可能とTab移動可能を同義にしない。

**例外と反証。** Adobeのダイアログ本体への復帰を、全製品の初期フォーカス規則へ拡張しない。内部操作をすべて除去した際に `document.body` へ落ちたり背後へ移動したりするかを確認し、対象の意味と読み上げ結果を別に評価する。

### 5. ネイティブ選択は要素名だけで完結しない

**確認した事実。** [USWDS Button](https://designsystem.digital.gov/components/button/#accessibility-guidance) は標準マークアップを勧め、見た目だけのボタンと実際の操作を区別する。ボタンの明示的な `type`、リンクに `disabled` を付けても停止しない点も説明している。

**提案 P5。** 操作か遷移か、フォーム送信か、キーボード契約と状態通知を誰が実装するかを選定表にする。既存ライブラリなら、その責任範囲を確認して利用する。「ネイティブを使ったから統合テスト不要」とはしない。

**反証。** フォーム内の閉じるボタンが送信する、無効化したつもりのリンクが移動する、ライブラリとアプリが同時に初期フォーカスを動かす。この探索ではHTML `dialog` の対応環境の網羅検証はしておらず、ネイティブ `dialog` を一律必須にする根拠には使わない。
