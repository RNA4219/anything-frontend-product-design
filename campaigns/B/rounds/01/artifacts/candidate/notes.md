# 予約 R-204 の日時変更 — 実装メモ

## 起動と成果物

このディレクトリで `node serve.mjs` を実行し、ブラウザで `http://127.0.0.1:8074` を開く。ポートを変更する場合は `node serve.mjs 8080`。サーバーはループバックアドレスだけで待ち受ける。依存パッケージ、ビルド処理、外部ネットワーク、実サービスへの接続は不要。

ES モジュールを使うため、`index.html` のファイル直接オープンではなく、上記のローカル配信を使う。

| ファイル | 内容 |
| --- | --- |
| `flow.mjs` | 指定インターフェースの状態機械。`createFlow(api, options)` をエクスポート |
| `index.html` | 日本語の操作画面。予約の現状・希望・確認・結果・回復を表示 |
| `app.mjs` | DOM の更新、ボタン操作、操作記録の保存・復元 |
| `mock-service.mjs` | 予約変更・照会・取消のローカルモック |
| `serve.mjs` | Node 標準ライブラリだけのローカル配信 |
| `smoke-test.mjs` | Node 標準テストランナーによる再現可能な確認 |

## 目的・開始条件・完了の証拠

タスク ID は `BOOKING-R204`。予約 `R-204` の最後に確認した日時は `2026-12-08T14:00`。希望候補は `2026-12-10T14:00` と `2026-12-11T14:00`。

変更の完了条件は、今回の操作 ID に対する `submit` または `lookup` が `succeeded` を返すこと。その時点で初めて `currentDate` を更新する。`succeeded` に `currentDate` がなければ、成功は要求した変更の成立を意味するというタスクの契約に従い、その操作の固定された `targetDate` を使う。`currentDate` があれば、その有効な日時を優先する。

`pending` の日時、通信エラー、取消受付、`not_found` は変更成立の証拠にしない。画面の旧日時は一貫して「最後に確認した予約日時」と表示する。応答喪失後は、サービス側ですでに変更が成立している可能性も明記する。

## コントローラのインターフェース

指定された `choose(date)`, `review()`, `confirm()`, `check()`, `cancel()`, `back()`, `view()` を返す。`confirm`、`check`、`cancel` は非同期。`view()` は指定の8項目だけを持つ新しいプレーンオブジェクトを返す。

操作 ID は送信時に一度だけ `nextId()` で作成する。予約 ID・変更希望・操作 ID を一つの固定ペイロードとして保持する。送信の連打は進行中の同じ Promise に合流し、別のサービス呼び出しを作らない。照会・取消の連打も各操作内で合流する。

追加の任意オプション `resume` は、ローカル UI の再読み込み復元用。保存済みの `view()` を渡すと、未確定操作は同じ操作 ID と希望日時で復元される。再送は行わず `unknown` から照会できる。必須の3オプションだけでも動作する。未確定記録が破損している場合は、黙って新しい変更を開始せずエラーとする。

## 状態・操作・保持データ

| 状態 ID | 利用者に伝える事実 | 操作と遷移 | 保持・更新するデータ | 結果の証拠 |
| --- | --- | --- | --- | --- |
| `editing` | まだ変更を送信していない | `choose` で希望を選択、`review` で内容確認 | 旧確認日時、希望日時。新規操作 ID は未作成 | ローカル状態 |
| `review` | 対象・変更前後を見直せる | `back` で編集、`confirm` で一度だけ送信 | 確認した希望。編集するとレビューは解除 | まだ副作用なし |
| `pending` | 送信中またはサービス処理中。変更成立は未確認 | `check`、未依頼なら `cancel` | 旧確認日時、固定希望、操作 ID | 送信開始、または `pending` 応答 |
| `unknown` | 通信や照会から結果を断定できない | 同じ ID の `check`、未依頼なら `cancel` | 固定希望と操作 ID を保持。別変更は不可 | 通信エラー、非権威的な照会ミス、再読み込み |
| `cancel_requested` | 取消要求の受付を確認。取消完了は未確認 | 元の操作 ID の `check` | 旧確認日時、固定希望、操作 ID | `{accepted:true}` |
| `failed` | 今回の変更は不成立 | 希望を見直し、再レビューして新規依頼 | 旧確認日時と希望を保持。次の送信は新 ID | `failed` |
| `succeeded` | 変更成立と確認できた日時 | 今回の目的は完了。必要なら別の変更を開始 | サービスの確定日時を反映 | `succeeded` |
| `cancelled` | 今回の日時変更処理の取消が成立 | 必要なら新しい日時変更を開始 | 旧確認日時と希望を保持 | `lookup` の `cancelled` |

未確定状態で `choose`、`review`、`back` を呼んでも、固定した希望と ID は変更しない。古い操作や終端後に到着した応答は無視し、遅れた `pending`、取消受付、通信エラーで確定結果を巻き戻さない。

## 再試行・取消の判断

本実装は、副作用のある `submit` の再送機能を提供しない。結果不明の場合は `lookup` に限定して回復する。したがって、24時間の冪等性期限が過ぎても、未知の結果を新しい ID でやり直すことはない。`not_found` でも未実行とは扱わない。長期的に照合できない場合は予約 ID、希望日時、操作 ID を保持し、サービス側の担当者による照合へつなぐ文言を表示する。このデモは問い合わせを実送信しない。

取消の対象は「今回の日時変更処理」。予約そのものの取消、クライアント通信の中止、成功後の Undo は提供しない。取消受付後も元の操作結果を照会する。`succeeded` なら変更が先行した結果を表示し、`cancelled` で初めて取消完了を表示する。取消要求の応答喪失後は、同じ画面から取消を重ねて送らず結果を照会する。

適用した判断の原典は、指定された `interaction-ux-flow` の `SKILL.md`、`references/async-outcomes.md`、`checks/flow-review.md`。B-IU-001（観測と業務結果の分離）、B-IU-002（意図・対象・内容・期限に基づく回復）、B-IU-003（取消受付と取消確定の分離）を採用した。外部資料へのアクセスは行っていない。これらは提供資料の設計上の推論として適用し、実バックエンドの保証として扱っていない。

## モックの契約と操作例

モックは `localStorage` にサービス状態を保持する。フロントの操作記録とは別のキーを使用する。予約変更は `succeeded` への遷移時に一度だけ反映する。処理時刻を保存し、次のモックアクセス時に経過時間を評価するため、ページを閉じている間も経過時間を再現できる。

| シナリオ | 試す手順 | 期待する結果 |
| --- | --- | --- |
| 正常動作 | 候補選択 → 確認 → 送信 → 約3秒後に結果確認 | `succeeded`、日時更新、成立回数1 |
| 変更拒否 | シナリオ選択 → 送信 | `failed`、日時は更新しない、候補を見直せる |
| 応答喪失 | シナリオ選択 → 送信 → 結果確認 | 送信は `unknown`。同じ ID の照会で最終結果へ到達 |
| 取消を試す | 送信後12秒以内に取消依頼 → 約2秒後に結果確認 | 受付時は `cancel_requested`、照会後は `cancelled` |
| 取消との競合 | 送信直後に取消依頼 → 結果確認 | 取消が受付されても、先行した `succeeded` を表示 |
| 照会エラー | 処理中に「次の照会を通信エラーにする」→ 結果確認 → 再確認 | 元の変更を失敗扱いにせず、同じ ID で回復 |
| 再読み込み | 処理中または結果不明でリロード → 結果確認 | 未確定の同じ操作を復元。送信回数を増やさない |

手動で「変更結果を確認」を押した時だけ照会する。バックグラウンドポーリングはなく、照会していない間を「確認中」と表示しない。処理中のデモ初期化を禁止し、未知の操作を初期化で消す導線を置かない。

## 仮定と残る制限

- 日時のタイムゾーンはタスクに指定がない。施設の現地時刻という文字列として扱い、端末のタイムゾーンへ変換しない。選択 UI は指定の2候補に限定する。コントローラの形式検証自体は他の有効な日時も受け入れる。
- サービスの `succeeded`、`failed`、`cancelled` は操作ごとに安定した終端結果であり、互いに矛盾する終端応答を返さないと仮定する。矛盾した正本を裁定するための版番号は契約にない。
- 実サービスが旧予約を原子的に保持するかどうかを UI だけでは保証できない。実導入の受入条件として、変更失敗・取消確定時に旧予約を失わないこと、希望枠への原子的な変更、同一 ID の内容一致・24時間重複排除をバックエンドで確認する必要がある。モックはその契約を模擬する。
- 24時間の期限後は照会が見つからないことがある。結果を解決できる管理 API や問い合わせ先は提供契約にないため、操作参照番号を残すところまでが実装範囲。
- 保存は同じブラウザ・同じ配信元の `localStorage` に限る。保存領域の手動削除、破損、別端末、別ポート、複数タブの競合、第三者による同じ予約の変更には対応しない。保存領域が利用できなければ開始を止め、稼働中の保存失敗は画面に表示する。
- キーボード用のネイティブボタン／ラジオ、ラベル、フォーカス表示、状態変化時の見出しフォーカス、`aria-live` を実装した。実ブラウザでの視覚確認、キーボード走査、スクリーンリーダー、モバイル端末操作は未実施。Node の制御テストと HTML の静的参照確認を、これらの検証済みとみなさない。
- モックの成立回数はこのローカル契約内での証拠。実サービスの原子性、利用者の文言理解、運用上の問い合わせ到達性を実証するものではない。
