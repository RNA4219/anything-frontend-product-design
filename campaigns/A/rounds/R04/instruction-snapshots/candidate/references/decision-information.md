# 判断情報の条件と確認範囲

A08–A10を、提供する作業・有効な条件・値の意味で補う。情報量を減らすこと自体を目的にしない。入力の要件やneeded_informationを、検査に通すために消さない。

## 1. 優先度と、提供する作業の情報義務を分ける — A08

1. 今回の案で提供する作業と、理由を付けて延期する作業を確認する。ここで「提供」は案に判断と経路を含める意味であり、稼働中の実装を確認した意味ではない。
2. 宣言されたgoal_routesではmust/should/couldにかかわらず、targetのrole、goalを担うkeep機能、needed_informationを照合する。should/couldは判断材料を省略する許可ではない。
3. 未提供の任意goalへ経路を一律に追加しない。共通支援機能F1が必須作業と将来の任意作業を支え、任意作業専用F2はdeferしている場合、F1のkeepだけで任意作業全体が提供済みとは推定しない。
4. 文章や画面だけで提供を約束し、goal_routesに表れていない作業は手動で照合する。必要なら経路を追加し、実際に延期するならその理由・影響・再検討条件を残す。

**確認:** 同じ作業・提供状態・必要情報のままpriorityだけを変えても、必要情報の義務は変えない。明示的に延期した任意作業と、共通支援機能だけを残す案は正例として確認する。

## 2. 条件と判断時点を固定して開示を決める — A08/A09

- role・対象・判断時点・有効条件を明記する。適用場面はbriefのcontent/contexts/constraintsや場面別のbrief・論理ビューで記録できる。新しい条件評価用のschemaを作る必要はない。
- 選択・棄却を変える具体値、適合条件、期限等をneeded_informationへ対応させ、その判断場所のprimaryにする。条件を判断するための値を、条件判明後にしか見られない場所へ置かない。
- 具体値と、その意味や手順を詳述する補助説明を分ける。説明でも当該判断に不可欠と確定した部分は必要情報に含める。それ以外の少数向け補足は、内容が分かる入口からの開示候補になる。
- 条件が非該当の補足や、後の判断だけで必要な情報を、前段の全画面へ複製しない。条件自体が不明なら、非該当と確定せず次節へ進む。

primaryはその判断場所で展開不要という本Skillの契約であり、スクロールを禁止しない。GOV.UKは一部利用者向けのDetailsを許容している。外部規格が全情報の折りたたみを禁止している、という説明にはしない。部品・展開動作・支援技術との関連付けはCへ渡す。

## 3. 不明・ゼロ・非該当を区別する — A08

| 入力の状態 | 判断での扱い | 避ける変換 |
|---|---|---|
| 根拠のある0/false | 定義・対象範囲とともに既知値として扱う | 0だから必ず欠測、と決める |
| 値が不明 | 情報項目、不明である状態、判断への影響、確認先を残す | 0円、無料、適合済み、falseへ補完する |
| 未計測と確認できる | 未計測と値の未知を保持する | 測定結果0と混同する |
| 適用条件から非該当と確認できる | 根拠を残し、その値の取得を強制しない | 条件も不明なのに非該当とする |
| 欠測理由も不明 | 理由を未確認のまま扱う | 未質問・秘匿・エラー等の原因を創作する |

必要値が不明でも情報IDを消さない。不明な重要条件を持つ候補は適合済みと確定せず、unresolvedへ担当・問い・影響を記す。必須達成を妨げる場合はblocking、別の確認済み候補で判断を進められる場合はその範囲を明示する。関係しない判断まで一律に停止しない。

欠測理由の存在自体が秘匿対象になる場合もある。判断と権限に必要な意味を保ち、全欠測理由の公開やHL7コードの採用を一般製品へ要求しない。

## 4. 密度を、比較する仕事から決める — A09

候補集合の大きさと画面の表示密度は別の変数である。対象分野に詳しいことと、今回の優先属性が定まっていることも分ける。

1. 初回理解、同時比較、反復処理のどの判断を支える案かを記す。
2. 同じ対象・必要属性・条件で配置案を比べる。候補を減らした結果、必要な適合候補や比較属性まで失っていないか確認する。
3. 頻繁な比較に必要な対応を保ち、補助説明を開示候補にする。熟練年数だけで必要情報を隠さない。
4. 収まり、画面往復、時間、誤り、選好のうち実際に確認した指標だけを報告する。既存visual_intentを保ち、実際の表現とレスポンシブはC/Art Directionへ渡す。

候補数・カード数・文字数・開示段数の万能な上限は作らない。候補数の研究から、密度の高い業務UIが常に速い、少ない候補が常に良い、と結論しない。

## 5. 確認できた層を分ける — A10

| 確認の層 | 実際に報告するもの |
|---|---|
| 原典 | 助言・用語定義・研究結果・著者の論考、該当箇所と限界 |
| Skillの導出 | 元の主張から追加した判断条件と、その理由・例外 |
| 意味照合 | 値、不明状態、適用条件、提供する作業の宣言を入力と照合した結果 |
| 構造検査 | ID、経路、targetの機能とprimary情報。値の正しさや条件の真偽は別 |
| 表示・操作 | 実際の表示、開示、着地。HTMLソースだけならその範囲 |
| 実利用 | 観測した人の完了、誤り、時間等。LLM別スレッドのレビューと区別 |

checkerの`information_values/information_applicability/optional_goal_delivery=false`は、値の意味、条件の成立、文章だけの任意作業提供を自動判定しないことを示す。情報IDがprimaryにあることは、値が既知で正しいことの証明ではない。visual_intent_idの一致だけで実画面の見た目を確認したことにもしない。

## 適用例

- 提供する「解約条件の確認」がshould: 通知日数・更新日・返金条件は、その確認場所で参照する。更新日が不明なら不明と示し、通知期限の日付を創作しない。解約処理はBへ渡す。
- 年間上限が不明なプラン: 上限0や無制限にせず未確認と記録する。別に全条件を満たす候補があれば、未知の候補を適合扱いせず比較を続けられる。
- 任意のデータ出力機能をdefer、共通の記録閲覧はkeep: 閲覧が残るだけでデータ出力作業の画面や経路を強制しない。
- 追加サービスを選択していない場面: その使い方の長い補助説明は開示候補。選択する場面で判断を変える料金や適用条件は、その判断場所へ戻す。

## 根拠と限界

- [DWP: What a component means](https://design-system.dwp.gov.uk/choose-a-component/how-to-choose-components/what-a-component-means) — R03-R1-S01。省略できる内容と、利用者のその時点の問いを扱う公式助言。
- [GOV.UK: Details](https://design-system.service.gov.uk/components/details/) — R03-R1-S02。一部向けの内容と、大多数が必要とする内容の区別。Detailsの全面禁止ではない。
- [DWP: How to choose components](https://design-system.dwp.gov.uk/choose-a-component/how-to-choose-components) — R03-R1-S03。必要情報と行為から考える実務上の出発点。固定規則やSkill効果の実証ではない。
- [Chernev et al., 2015](https://chernev.com/wp-content/uploads/2017/02/ChoiceOverload_JCP_2015.pdf) — R03-R2-S01。商品選択に関する条件と調整要因。2016訂正文の直接取得に制限があるため、詳細効果量は採用しない。
- [Scheibehenne et al., 2010](https://bear.warrington.ufl.edu/brenner/mar7588/Papers/scheibehenne-jcr2010.pdf) — R03-R2-S02。研究間のばらつきと平均の限界。2015年の分析と元研究が重複し、独立した二回の再現とは数えない。
- [HL7 DataAbsentReason](https://terminology.hl7.org/en/CodeSystem-data-absent-reason.html) — R03-R2-S03。unknownとnot-applicable等を区別する医療用の語義。一般UIの表示規則や判断改善量の実験ではない。

政府ガイド等は2026-11-23に確認した該当箇所に限る。これらの資料から本Skillの利用者効果を直接証明したとは扱わない。
