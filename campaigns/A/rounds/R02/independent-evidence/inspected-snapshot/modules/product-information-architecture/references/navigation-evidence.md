# 探索・旧入口・選択場所の条件

A05–A07の条件を補う。カテゴリ数、画面数、入口数を一律に決める資料ではない。変更に関係する項目だけを確認し、判断を変えない未知を理由に全作業を停止しない。

## 1. 検索結果を読む範囲を決める — A05

**適用:** カテゴリとフィルタを再編するとき、検索0件を根拠に対象の存在や機能の必要性を判断するとき。

1. 目標ごとに対象集合・role・scope・比較属性・有効な絞込を並べる。同じ対象の別カテゴリ所属や保存ビューは正本IDへの対応として扱う。
2. 0件という観測はそのまま残し、検索語・集合・権限・絞込・索引対象/更新の範囲を確認する。限定検索の0件を全体の不存在へ拡張しない。別名・語形・条件解除で判断が変わる可能性を残す。
3. 検索・フィルタが設定されていることと、対象画面・role・集合規模で実際に提供されることを分ける。必要な入口が非表示になる場合は、代替経路またはB/Cへの依存を残す。
4. 分割により必要な横断比較が壊れないか、統合により必要なフィルタや権限境界が失われないかを両方調べる。カテゴリ固有属性や対象が異なる場合は分割を維持できる。
5. 表示ラベルをまとめること、元属性を変更すること、対象の正本化を別に記す。同じ表示名を同一対象の証拠にしない。

**例外:** 母集団・権限・索引・条件が当該判断に十分なら「この範囲・条件では該当0件」と記録してよい。すべての既知対象検索へファセットを要求しない。製品固有の件数制約を一般的なカテゴリ分割閾値にしない。

**確認:** 同じ正本集合で、既知対象を1件探す課題と、複数属性の候補を探す課題を分ける。成功・取りこぼし・時間・選好を混ぜない。未実施なら効果は未確認のままとする。

## 2. 正本と入口を別に扱う — A06

**適用:** 名前変更、カテゴリ統合、旧メニュー・ブックマーク・深いURL・外部参照の移行。

1. 正本の数と入口の数を分ける。同じ正本への複数入口を残してよい。別のrole・対象・成果を、同じ画面へ着くことだけで統合しない。
2. 実在する旧入口を種類ごとに列挙し、従来の目的・対象・scope・roleと、維持/後継案内/明示終了/未確認の扱いを対応させる。これらは作業上の区別であり、新しいdispositionのenumではない。
3. 旧入口が開くだけで移行済みにしない。同一対象または確認した承継先へ、必要な成果と条件を保って着くか確認する。同名の別対象への再割当て、一部経路だけの転送失敗を反例にする。
4. 通常の探索先と、前段の入力・選択・状態を要するプロセス途中/結果を区別する。途中画面の独立入口を一律要求しない。再開や直接参照が必要なら、前提を回復できる条件をB/Cへ渡す。
5. 旧入口を終了する場合は[A03の廃止条件](feature-context.md)を使い、理由・失う成果・後継があればその案内を残す。永久保持や、後継のない終了の一律禁止は導かない。

**確認:** 旧メニュー、ブックマーク、外部参照等について期待対象と実際の着地を別々に照合する。Webリンクの成功を連携や保存状態の成功へ拡張しない。URLやID文字列の完全一致ではなく、対象承継と必要条件を見る。

## 3. 選択時の意味と宣言targetを照合する — A06/A07

次の対応をrationale、notes、decision_notesへ短く残す。新しいトップレベル項目は不要。

| 記録するもの | 確認すること |
|---|---|
| 開始場所・操作 | 検索候補の選択、Enter、保存検索等を同じ経路と誤認していないか |
| 表示ラベル＋関連文脈 | 選択する時点で対象・範囲・行為を識別できるか |
| 期待対象・粒度 | 商品全体とvariant、同名別資料等を取り違えていないか |
| 実際の判断場所 | 比較・選択に使う情報と機能がそこにあるか |
| 宣言target・実際の着地 | goalの完了条件と対応し、別対象へ無説明に置換していないか |
| 確認状態 | 設計上の対応、HTMLソース照合、実操作、人の理解を区別したか |

短い「詳細」が複数あっても、選択時に使える関連文脈と合わせて目的を特定できる場合がある。文字列の完全一意化や着地タイトルとの完全一致を強制しない。一方、別画面の記憶や、到着して初めて分かる説明を、選択時の文脈に数えない。視覚的な近接だけで支援技術への関連付けが成立したとは扱わない。

比較・選択で完了するgoalなら、その判断を行う画面をtarget_screenへ対応させる。保存完了等がgoalなら、その完了条件に沿うtargetを選び、前段の比較情報も必要な場所へ残す。すべてのgoalを一覧画面または完了画面の一方に固定しない。

checkerは同名リンクの関連文脈を検査できずHOLDにする。実UIに存在する文脈を含む識別表記をlabelへ記録する場合は、元の短文言と対応箇所も残す。説明文を追加しただけで実装やラベル理解が確認済みになるわけではない。

## 適用例と反例

- 「登録済み研修」内の検索0件: 現在の範囲・条件の0件として表示し、必要なら全公開研修を探す入口を示す。全研修が存在しないと結論しない。
- 旧`/training/basic`がC-101を指していた: 同名C-202へ転送できても対象を取り違えている。確認したC-101または承継先へ対応させる。
- 一覧の各行に「詳細」がある: 対象名との関連文脈を確認する。未確認ならHOLD、識別できないことが実際に確認されたなら具体的な欠陥として修正する。
- 申込完了画面: 単独メニューがないことだけで不合格にしない。申込の前段、再開要件、通常の探索先を分ける。
- 統合後の大集合で必要なフィルタが提供されない: 共通属性だけで強制統合せず、分割＋横断探索や実装変更と比較する。
