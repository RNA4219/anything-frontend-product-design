# チーム向けプラン比較：設計判断

## 結論

**P-300 / Team Proだけが、支給データで12人・年間900,000件・年総額130,000円以内の全条件を満たすと確認できる。** 3候補を同じ比較表に置き、P-100の「不適合」とP-200の「未確認による判断保留」を区別する。契約期間と価格基準も同じ判断場所に示す。

現契約CT-75の解約条件は同じHTMLの独立した判断領域で提供する。通知日数30日、次回更新日「未確認」、返金条件「途中解約による返金なし」を展開なしで読む構成とする。更新日がないため通知期限の日付は出さない。候補の判断・条件の確認が今回の成果であり、購入・解約・選択保存の完了を示さない。

## 1. 入力・事実・仮定

入力は `common/brief.json`、`common/task.md`、`common/plan-contract.md`。2026-11-23に取得した支給内容を固定して使用した。revisionは未提供。方法は指定の `anything-frontend-product-ia` と、その目標・情報構造・探索・開示・判断情報のreferencesに従った。契約は共通1.1を採用した。

| 区分 | 内容 | 判断への影響 |
|---|---|---|
| 依頼で確定 | buyer（契約担当者）、own-organization、buyer-account | 自組織の契約担当者向け。別役割・別組織の機能は追加しない |
| 依頼で確定 | 必要人数12人、年間利用900,000件、年総額上限130,000円 | 人数上限≧12、年間上限≧900,000、年総額≦130,000で照合する |
| e_case / requirement / verified | 記載された合成候補条件と提供範囲のみ | 実在商品の仕様や利用者の観測データへ拡張しない |
| e_missing / unknown / unknown | P-200の年間上限、CT-75の次回更新日 | 不明のまま表示し、それぞれの判断への影響を残す |
| 依頼で確定 | 主タスクは3候補の横断比較、補助タスクは既存契約条件の閲覧 | 比較値を候補別ページへ分断せず、解約条件は別の判断領域にする |
| 依頼で確定 | 初回利用者向け説明と、繰返し比較で不要な往復を避けること | 短い用語説明と共通属性の比較表を同居させる |
| 仮定・提案 | 未確認値を契約資料・条件提供元・管理窓口に照会する | 具体的な資料や窓口の存在・URLは未確認。確認手順の提案として表示する |
| 未指定 | 契約期間の追加合否条件、端末条件、実利用頻度、既存URL | 12か月を比較情報として保持する。実測や移行済み状態を創作しない |

固定データを越える商品選択肢、料金、割引、税率、法規則は追加していない。

## 2. 目標–要件–機能

| 役割・目標 | 完了を判断する材料 | 要件・必須性 | 対応機能・今回の提供 |
|---|---|---|---|
| buyer → g_select（must）：12人・年間90万件・年総額13万円以内の確定条件を満たす候補を選ぶ | plan_id、seat_limit、annual_quota、annual_total、commitment | r_select、mandatory=true：上限・年総額・契約期間を同じ場所で比較。不明な上限を適合済みや0にしない | f_plansをkeep。s_compareの比較表で候補を判断する |
| buyer → g_review_cancel（should）：現契約の解約条件と期限判断に不足する情報を確認する | contract_id、notice_days、next_renewal_date、refund_rule | r_cancel、mandatory=false：今回、解約条件の確認を提供。解約実行は対象外 | f_cancel_infoをkeep。s_cancelで条件と不足情報を確認する |

両目標とも今回の案で提供するので、優先度にかかわらず必要情報を各判断領域のprimaryにする。shouldを「必要な具体値を隠してよい」という意味に使わない。

### 機能判断

| 機能ID | 処置・正本 | 優先度と根拠 | 維持する条件 |
|---|---|---|---|
| f_plans | keep / target=null | required。mustとmandatoryの候補選択に必要 | object=plan、outcome=select-qualified-plan、roles=[buyer]、goal_ids=[g_select]、requirement_ids=[r_select]、dependencies=[] |
| f_cancel_info | keep / target=null | high。補助タスクだが期限・返金条件の判断に関わり、今回提供する指定がある。期限の切迫度・利用頻度は不明 | object=contract、outcome=review-cancellation-conditions、roles=[buyer]、goal_ids=[g_review_cancel]、requirement_ids=[r_cancel]、dependencies=[] |

どちらも入力はscope=own-organization、lifecycle=existing、availability=available、context_constraints=[buyer-account]、evidence_refs=[e_case,e_missing]。f_plansのmandatory=true、f_cancel_infoのmandatory=falseを変更していない。対象と成果が異なるので、同じHTMLへの配置を理由に機能をmergeしない。追加・削除・延期も行わない。

## 3. 固定値による比較と未知の扱い

| 判断材料 | 必要条件 | P-100 / Team | P-200 / Team Plus | P-300 / Team Pro |
|---|---|---|---|---|
| 人数上限 | 12人以上 | 10人：2人不足 | 20人：8人余裕 | 20人：8人余裕 |
| 年間上限 | 900,000件以上 | 1,000,000件：100,000件余裕 | null / 未確認 | 1,200,000件：300,000件余裕 |
| 年総額 | 130,000円以下 | 96,000円：34,000円余裕 | 110,000円：20,000円余裕 | 120,000円：10,000円余裕 |
| 価格基準 | 同じ基準で比較 | 税込・12か月総額 | 税込・12か月総額 | 税込・12か月総額 |
| 契約期間 | 追加条件の指定なし | 12か月 | 12か月 | 12か月 |
| 全体判定 | 3条件すべて充足 | 不適合：人数不足 | 判断保留：年間上限未確認 | 適合：確定条件から選べる候補 |

これは入力値の比較と算術から導いた結論。P-200は110,000円なので、年間上限が後から確認できれば候補判断に影響しうる。そのため候補から削除せず、適合とも不適合とも確定しない。「最安の適合プランがP-300」とは断定しない。P-300によって今回の確定条件を満たす候補を選べるため、P-200の確認待ちで全体を止めない。

| 現契約の項目 | CT-75の入力 | 判断できる範囲 |
|---|---|---|
| contract_id | CT-75 | 条件の対象を特定できる |
| notice_days | 30日 | 通知日数の値を確認できる |
| next_renewal_date | null / 未確認 | 次回更新日の具体的な日付は分からない |
| refund_rule | 途中解約による返金なし | 返金条件を確認できる |
| 通知期限の日付（判断結果） | 算出しない | 次回更新日がないので期限内・期限超過も判定できない |

未確認の原因は入力にないので推定しない。次回更新日は0や「非該当」に変換せず、確認すべき情報として残す。現契約の条件を候補3プランへ転記しない。

## 4. 情報構造・入口・画面責務

`preview.html`一枚に、2つの論理的な判断領域を順に配置する。`plan.json`のscreensはこの領域に対応する。実ページを2枚へ分割したという意味ではない。

| 領域 | 一つの判断 | 正本機能 | primary | secondary |
|---|---|---|---|---|
| s_compare / 3候補のプラン比較 | 3条件を満たす候補はどれか | f_plans | 必要条件、候補ID、人数上限、年間上限と未確認状態、年総額、価格基準、契約期間、判定と根拠、短い用語説明、P-200の確認項目 | 請求書の宛名テンプレートの説明、過去バージョンのヘルプ改訂履歴 |
| s_cancel / 現契約CT-75の解約条件と不足情報 | どの条件が分かり、期限判断に何が不足するか | f_cancel_info | 契約ID、通知日数、次回更新日と未確認状態、返金条件、期限日付を判断できない理由、確認項目 | なし |

primaryは展開操作が不要という意味で、最初の画面内に必ず収まるとは主張しない。比較表は同じ列に同じプラン、同じ行に同じ属性を置く。人数・年間上限・年総額の条件と判定根拠を合わせて読む構成とする。

補足だけを標準HTMLのdetailsに置き、summaryに「請求書の宛名テンプレートの説明／過去バージョンのヘルプ改訂履歴」と内容名を表示する。補足本文は入力にないので未提供と書く。空の外部リンクや架空のヘルプ記事を作らない。

### 経路と選択時の文脈

| 開始→着地 | 表示ラベル | 種類・文脈 | 宣言targetとの対応 |
|---|---|---|---|
| buyerの入口→s_compare | 3候補のプラン比較（見出し） | buyer-accountを前提に自組織の3候補を比較 | g_selectの判断場所は比較表そのもの。start=target=s_compare |
| s_compare→s_cancel | 現契約 CT-75 の解約条件と不足情報 | contextual。選択時から対象CT-75と読む内容が分かる | #s_cancelにCT-75の4必要情報が存在。g_review_cancelのtargetと一致 |
| s_cancel→s_compare | 3候補のプラン比較へ戻る | local。同じ検討領域の比較へ戻る | #s_compareに同じP-100/P-200/P-300が存在 |

リンクラベルと着地の対応はHTMLソースで確認した。ブラウザーで移動を実行したという意味ではない。固定3件をすべて表示するので検索・フィルタは追加しない。旧メニュー・ブックマーク・既存URLは未提供で、移行や旧入口の対象承継を確認済みとしない。

## 5. 採用案と代替案

| 案 | 判断 |
|---|---|
| 共通属性の比較表＋別の解約条件領域 | 採用。3候補の条件を同じ場所で照合し、別対象CT-75の条件も明確な入口から読める |
| 候補ごとの詳細ページ・ウィザード | 不採用。今回必要な同時比較を分断し、記憶や往復を必要とする |
| 価格中心のカードと、上限の詳細開示 | 不採用。P-100の人数不足、P-200の年間上限未確認を判断時点で読めなくなる |
| 解約条件をまとめて折りたたむ | 不採用。今回提供するg_review_cancelの必要値をprimaryに保てない |
| 解約条件まで一つの比較表に混在させる | 不採用。候補プランと現契約CT-75の対象を混同しやすい構造になる |

これらは入力と必要情報に基づく設計判断で、処理時間の短縮や利用者の誤り減少を実測した結果ではない。

## 6. 維持する視覚意図と引継ぎ

visual_intent_idは **existing-team-admin** をそのまま保持する。制約原文：

> 視覚資産未提供。標準HTMLで情報構成を示す。独自意匠の採用や既存UI再現を主張しない。

HTMLにはCSS、JavaScript、外部フレームワーク、画像を追加していない。見出し・表・説明リスト・ページ内リンク・補足のdetailsで情報関係を示す。独自配色や既存UIの再現、視覚的な完成を主張しない。

## 7. 検証した範囲と未確認

**自作の構造・HTMLソース照合済み、効果未確認。** 正式な品質PASSや実タスク成功率は主張しない。支給checkerの実行は指定読み取り範囲外なので行っていない。

| 層 | 実施状況・結果 |
|---|---|
| 入力と対応 | 全2機能IDの一意性、目標・要件・役割・範囲・利用条件・証拠参照の保持を照合 |
| JSON | Python標準ライブラリで構文、共通1.1のトップレベル、参照先、buyerの経路、keep機能、宣言した両goalのprimary情報を確認 |
| 固定値と意味 | 表の3候補とCT-75、人数・利用量・金額・期間、2つの未知値、適合/不適合/判断保留の根拠を支給データと照合 |
| HTMLソース | HTMLParserでIDとアンカーの対応、各必要情報が該当sectionにありdetails内にないこと、全3候補の同一表配置、外部スクリプト・フォーム等の不在を確認 |
| 正式checker・そのテスト | 未実施。自作チェックの結果を公式checkerのPASSと呼ばない |
| ブラウザー描画・実操作 | 未実施。環境でブラウザーがブロックされているとの作業条件に従い起動を再試行していない |
| 実利用者・独立評価 | 未実施。理解度、完了率、作業時間、画面幅への適合は未確認 |

自動検査が意味や利用者の判断を代わりに証明しないという境界を保持する。`navigation_context`、`search_coverage`、`legacy_entry_identity`、`rendered_goal_location`、`information_values`、`information_applicability`、`optional_goal_delivery`は自動判定で確認できた範囲に含めない。値と任意目標の提供は、上記の入力・ソース照合として別に確認した。
