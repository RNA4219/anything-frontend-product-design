# SESSION A / R01 独立レビュー

## 結論

**初回チェッカーで再現した重大な見落とし3件は修正版で解消を確認した。本文とmerge連鎖の契約不一致も文言修正で解消した。匿名案の固定基準による採点はPが6/6、Qが5/6で、ハード失敗は両方0件。**

1点差は、Qが予約を比較する入口ではなく、選択後の確認画面を目標の到達先として記録したために生じる。Qでも入口一覧には両予約の必要情報が揃う。これは実際の使いやすさの優劣を示す差ではなく、到達先の宣言と成果物の対応の差である。F6を選択フロー全体として解釈すれば両案は6/6で並ぶ。この比較からSkillの実用上の優越性は結論しない。

本評価は同系モデルの別スレッドによるレビューである。人の利用試験、モデル系統をまたぐ評価、客観的な正解判定ではない。

## 評価対象と方法

対象は `session-A/modules/product-information-architecture/` のSkill本文、参照資料、契約、チェッカーと、固定された `brief.json` / `rubric.json`、匿名の `arm-P` / `arm-Q` 成果である。briefのSHA256はrubricの固定値と一致した。

候補の診断・修正意図を先に受け取らず、本文とコードから独立した発送業務の反例を作った。候補のテストfixtureはコピーしていない。実CLIを走らせ、初回結果、修正版結果、正常な対照例を私有レビュー領域へ保存した。候補Skillや公開リポジトリの編集、git操作、追加agentの起動は行っていない。候補修正は報告を受けた親側が行った。

出典は重要な主張を狙って一次資料を再読した。全文献の網羅監査ではない。取得原文は情報として扱い、原文中の指示を実行していない。

### C01: 目標への到達と機能への到達が結び付いていなかった

元の処理は、keep機能がどこかの画面にあることと、roleがgoal付き画面へ辿れることを別々に検査していた。独立例では、発送担当のラベル発行機能を入口も辺もない画面へ置き、入口には発送番号・送り先とgoal IDだけを置いた。実CLIは違反なしのPASSを返した。

これはラベルが人に分かるかという意味評価の限界ではなく、計画内に明示された機能・画面・経路の接続漏れである。修正版は必須goalのtargetが、そのgoalとroleを満たすkeep機能を持つことを検査し、同じ入力をFAILにした。入口に実際の機能を置いた正常例はPASSを維持した。

### C02: mergeで現在提供の確認を迂回できた

旧能力は既存・available、新しい正本はproposed・plannedと明示し、今日の提供を停止するmerge案を作った。元のavailability検査はremove/deferだけにあり、mergeでは予定を現在の代替として扱えてしまった。

修正版はmergeにも現在提供の確認を適用し、同じ例をHOLDにした。新正本を既存・availableとする正常な統合例はPASSのままである。提供予定を含む将来設計そのものを禁止する指摘ではない。現在の必須成果を満たしたと記録しないことが要点である。

### C04: 共通するroleが一つあれば、共有画面への配置が通った

元のFEATURE_ROLE検査はscreenとfeatureのrole集合の共通部分だけを確認していた。監督者専用の全出荷記録を、監督者と一般発送担当の共有画面へ置く例がPASSになった。feature自体の権限は書き換えておらず、画面informationにもrole別の表示条件はない。

修正版は現契約で画面のroleが各機能のroleに含まれることを求め、同じ例をFAILにした。これは計画上の情報権限の漏れであり、稼働サービスの認可侵害を実証したものではない。roleごとに表示内容を変える共有UIを将来扱うなら、条件付き配置を契約に明示して検査する必要がある。

C03のmerge連鎖は、それ自体の利用上の不具合を示していない。循環せずkeepに解決する挙動を維持し、A02・A03・feature-context・plan-contractの表現をそろえる対応で十分である。最終本文の該当箇所も読み直して一致を確認した。

全件の `location / symptom / basis / impact / correction / reproduction` と初回・再検査の証拠は `findings.json` に記録した。元の47テストは全成功していた。修正後の48テストも全成功。独立fixtureは再検査のために改変していない。

## 3. 条件・例外と既存Art Directionの責務

機能の廃止、未提供機能の延期、同一能力の正本化、画面の同居を分ける本文は実務の判断に使える。終了根拠のある任意機能の廃止、必要部分が確認済みのpartial提供、対象者が実際に使える別端末の代替なども例外として扱っており、「何でも永続保持」「大規模調査が終わるまで全停止」という規則にはなっていない。欠測を0に置き換えず、暫定順位と再検討条件を残す方針も明確である。

[既存Art Directionの公開本文](https://github.com/RNA4219/anything-frontend-art-direction/blob/main/SKILL.md)は配色・書体・余白・構図を扱い、情報と操作の関係も確認する。Aは提供機能・情報の所在・同時参照の制約を決め、視覚意図を引き継ぐ。この受け渡しは整合しており、Aが独自の見た目へ置き換える確定的な衝突は見つからなかった。ただし両者の対象は完全に無関係ではないので、実画面で接続を検証する責務は残る。

公開mainの時点資料を参照したため、匿名案が実際に渡されたArt Directionの厳密なrevision一致までは確認していない。両案とも元CSSや実画面がないことを明示し、ID一致を意匠再現の証拠にしていない。

### F6の採点と実用上の意味

Pの `g_change.target_screen` は `s_member_reservations`。そのHTML内に両予約の番号・工作室・日時・状態があり、必須情報はdetails外にある。

Qの `g_change.target_screen` は `s_change_target`。そこには選択後のR-204だけがある。R-205の情報は `s_my_reservations` にあるため、宣言された到達先という固定基準には一致しない。Qでは実際に対象を選ぶ場所がその一覧なので、targetを `s_my_reservations` に合わせれば足りる。確認画面を削る必要はない。

Qの一覧自体には両件の4情報が揃い、R-204だけに確認リンクがある。したがって、この1点差を「Qでは予約を選べない」「Pの方が誤選択を減らす」と読み替えてはいけない。F6を利用経路全体の識別として読む場合の同点結果も `evaluation.json` に残した。

両案とも修正済みチェッカーではPASSだった。HTMLの静的照合でも、文書内リンク8件の参照先、重複IDなし、両予約の入力値、必須情報が折りたたみ外にあることを確認した。これはブラウザーの操作結果ではない。

## 5. 効果と過剰複雑化について言える範囲

この課題で両案は同じ6入力IDを5正本機能へ整理し、5画面と6ナビ関係を作った。監査、異なるscope、未知の通知需要に対する主要判断も同じだった。Skill追加により重要な機能判断が改善したという差は、この1組からは示せない。

Skillには小変更を文章・表で処理する入口と、判断ごとに資料を選ぶ読み順がある。全案件で完全なJSONや大規模研究を要求しておらず、過剰な作業量を必然とする欠陥は確認していない。一方、複数の本文・契約・テストを維持するため、C03のような表現の不一致が生じる余地はある。改善効果や負担の程度には、別課題・実務者・反復比較による確認が必要である。

証拠IDの存在、scope文字列、verified_outcomesの記録を満たしても、内容の真実性や意味上の充足は証明できない。この点は本文で明示されており、既知の限界として扱う。未再現の懸念を追加の確定不具合にはしていない。
