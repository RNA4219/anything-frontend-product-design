# 分類変更で対象・所属・探索条件を保持する

既存の分類、タグ、カテゴリ、保存ビューを再編するときにA05–A07と併用する。目的は、分類表が埋まったことと利用者が必要な対象を探せることを混同しないこと。小さな改名は短い表でよく、無関係な全製品の棚卸しは要求しない。

## 1. 変更前の範囲と関係を固定する

revisionまたは取得日時、取得したscope、関係するrole・goal、維持条件、依頼ですでに認められた変更を記録する。新しい承認フローを一律追加する意味ではない。取得範囲が一部なら、その部分集合として扱う。

| 関係 | 区別して記録するもの |
|---|---|
| 対象の同一性 | 実レコードID、同一対象または確認済み後継との対応 |
| 分類の意味 | 概念ID、表示名・別名、分類軸、意味範囲、共有/局所scope |
| 分類の構造 | 親子関係、概念間mapping、子孫・共有部分・場所固有部分への作用 |
| 分類への付与 | レコードID → 概念ID。複数所属を許す |
| 探索 | role・goal・scope・実在する入口 → 対象集合、必要な絞込条件、判断場所 |

feature/screen IDを実レコードIDの代用にしない。概念間の対応は、レコードの同一性や所属付与とは別の関係である。名称が同じだけで統合せず、名称だけ変わった同一対象も区別する。識別子が未提示なら、同名照合で未確認を埋めない。

## 2. 変更操作の作用を分ける

改名・移動・複製・共有・分割・統合・終了ごとに、どのID・意味・関係を変えるかを書く。親への操作から全子孫の同じ変更を推測しない。製品のcopy/merge等は、当該仕様を確認する。

SKOSのexactMatchは同一資源を意味するsameAsとは異なる。概念mappingからレコード併合、所属の全移植、周辺の親子/関連関係の継承へ飛躍しない。別製品の「完全一致」にSKOSの仕様を当てはめない。SKOS/RDFの導入は不要で、関係を区別した表でもよい。

根拠のある1対多・多対1・多対多、ID変更、範囲変更、追加・終了を許す。旧レコードのどの部分集合がどこへ行くかを記し、すべての旧対象をすべての後継へ複製して未対応を消さない。

## 3. 取得範囲内のIDと所属を照合する

1. 対象ID集合と、レコード→概念の所属集合を別々に列挙する。正本数、概念数、所属数、到達可能な対象数を同じ「件数」にしない。
2. 旧対象を、同一対象保持、確認済み承継、意図した終了/範囲外化、未確認に分ける。これは説明の区分であり、plan 1.1の新しいenumではない。新規追加は別に記す。
3. 対象IDと所属を期待する変更に照合し、説明できない欠落・追加・未付与・所属変更・対応不能をID付きで返す。概念mapping全行の充足だけでは足りない。
4. 総数もカテゴリ別件数も同じまま、対象の入替や所属交換が起こり得る。件数は診断の補助値にする。標本確認は有効だが、未観察範囲の保証へ拡張しない。
5. 未使用語の整理では、該当scopeの所属と他の参照・子孫・入口を分けて確認する。部分検索の0件を「未使用」と断定しない。実在しない旧入口を創作しない。
6. 取得範囲内の差分、意味レビューした境界/標本、未確認集合、母集団自体が不明なscopeを分ける。全件構造照合は全件の人手意味レビューではない。全role×全itemの人手試験や普遍的件数上限を要求しない。

必要なら後述の比較補助を使う。差分の存在だけで不合格にせず、意図した変更と照合する。必須保持条件を妨げる未解決だけをblockingにし、無関係な不足で確定部分まで止めない。

## 4. 探索軸・入口・判断場所へ戻す

主題、対象者、職務、場所、用途、保全状態等の何を表す分類かを明示する。分類のlocal/global利用範囲、navigationのglobal/local/contextual、閲覧認可を混同しない。

影響するrole・goal・scope・旧入口について、探せた対象集合と必要な絞込・比較条件を、新入口と担当画面へ対応させる。総合一覧が開く、管理者だけが辿れる、全体検索に出る、といった確認を別roleの探索保持へ拡張しない。

同じ正本への複数分類・別名・局所ビュー・役割別入口を候補に残す。目的・対象・scopeが同じ重複は統合できる。件数を均等にするだけの下位分類は作らない。分類共有、画面共用、機能mergeは別判断である。

必要候補集合・横断比較・識別属性・必要絞込・needed_informationを判断場所で扱えるか確認する。区別を消す統合と、比較を壊す分割の両方を点検する。画面の見た目は既存visual_intentを保ち、Art Directionへ渡す。

## 5. 出力と責務

対応と根拠はdecision_notes、入口の条件はnavigation.rationale/goal_routes.notes、残件はunresolvedへ記す。分類所属をfeatures.targetへ入れず、plan 1.1の正本化・廃止条件を保つ。小変更は同じ意味を短い文章・表で返してよい。

索引反映・転送・認可・状態・再開はB/C、利用者の発見・理解・判断成果はDへ渡す。構造、意味、実操作、人の結果を別に報告する。旧入口の永久維持は要求せず、既存A03の廃止条件と必要な後継案内を確認する。

## 任意の比較補助

`checks/compare_inventory.py`は、取得済みの正規化snapshot間で宣言フィールドを比較する。実プロダクトへの書込みや概念mappingの自動適用はしない。これはplan 1.1とは別の任意のデータ受渡し形式で、すべての案件へ追加ファイルを強制しない。

```sh
python checks/compare_inventory.py --before before.json --after proposed.json --output comparison.json
```

両snapshotはcase_id、revision、concepts、records、entriesを持つ。空の集合も[]で示す。proposed側のbasis_revisionに比較元のrevisionを記す。

| 集合 | 必須の各行フィールド | 任意・注意 |
|---|---|---|
| concepts | id, label, axis | scope, parent_ids。親子関係の意味・循環の可否は判定しない |
| records | id, label, scope, roles, concept_ids | roles/concept_idsは文字列配列 |
| entries | id, path, role, scope, concept_ids | 実在する入口だけを列挙。空配列も可 |

各IDは集合内で一意。スカラーは空でない文字列、配列の要素は重複のない空でない文字列。欠けた事実を形式のために推測せず、必要な正規化ができなければ表で確認する。roles、concept_ids、parent_idsは順序を意味にしない。

出力は**COMPARED / decision: NOT_EVALUATED**であり、変更の採用や品質PASSではない。exit 0は比較処理が終わったことだけを表す。入力の型・重複IDに問題があればINVALID_INPUT / exit 2。旧新basisの不一致、取得集合外への参照、未検査フィールドも返す。入力に書かれた変更理由を自動的な承認根拠にしない。

出力先がbefore/afterと同じパス、またはsymlink/hardlinkで同じファイルを指す場合は、入力を保つため書込みせずexit 2で拒否する。通常は別名のcomparison.jsonを指定する。

追加/削除ID、同一ID内のフィールド変化を、対象・概念・入口ごとに返す。正当な改名や未使用分類の整理も差分として出るので、与えられた変更根拠で解釈する。異なるID間の同一性・承継は推定しない。**差分0でも、取得母集団の完全性、源データの真偽、意味の同一性、認可、索引反映、人の探索成功は未確認**である。

## 根拠と導出の境界

- [R04-R1-S01: SKOS Reference](https://www.w3.org/TR/skos-reference/) §1.2、10.6.7–8は概念/ラベル/関係、mappingの意味を扱う。レコード移行の成功規範ではない。
- [R04-R1-S03: SKOS Primer](https://www.w3.org/TR/skos-primer/) §3.3は資源への主題付与とSKOSの範囲を説明する。同系統の非規範文書で、独立実証ではない。
- [R04-R1-S02: NISO Z39.19-2005(R2010)](https://groups.niso.org/higherlogic/ws/public/download/12591/z39-19-2005r2010.pdf) §11.3.2.1–2は既存索引への用語変更影響を扱う。確認した歴史的版で、現行性は未確認。
- [R04-R2-S01: GOV.UK Taxonomy principles](https://www.gov.uk/government/publications/govuk-topic-taxonomy-principles/govuk-taxonomy-principles)は主題分類の目的・範囲と運用上の標本確認を扱う。全分類を単一軸へ統一する一般規範ではない。
- Microsoftの[R04-R2-S02: Introduction to managed metadata](https://learn.microsoft.com/en-us/sharepoint/managed-metadata)と[R04-R2-S03: Create and manage terms in a term set](https://learn.microsoft.com/en-us/sharepoint/create-and-manage-terms)は、その製品の共有/局所範囲や分類操作を扱う。他製品の挙動へ一般化しない。

ID・所属の残差照合とこのPython形式は、原典の範囲を既存A05–A07へ適用した設計上の導出。原典が同じJSONや全件人手検査を義務付けたわけではない。取得証跡は選択抜粋と位置情報であり、原典全文保存の証拠ではない。
