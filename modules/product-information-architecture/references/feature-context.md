# 機能変更の条件を照合する

A01–A04の改訂。機能を統合・削除・延期する場合だけ読む。以下は原典の規定そのものではなく、公式ガイドと製品の一次事例から導いた設計手順である。

## 1. 影響範囲と証拠

- 機能の削除・延期・統合を検討するとき、影響する目標ごとに『どのroleが、どの対象範囲で、どの条件の下、何を達成するか』を記述し、要求された画面・部品・機能名と達成結果を分ける。既存IDとの対応を残す。
- 変更で影響する利用者を確認する。顧客側の操作だけでなく、入力に現れる支援・運用・連携担当と、その作業や依存を含める。関係が未確認の役割は影響調査の候補とし、架空の必須要件にはしない。
- 達成内容と利用条件の各主張に、観測、利用者・担当者からの報告、依頼で確定した条件、仮定、未確認の別と出所を付ける。報告や依頼による確定と、利用実績の観測は同一視しない。
- 役割・対象範囲・成功条件の不明点によって候補の削除・統合可否が変わるなら、影響する機能の保持案と確認課題を残す。判断に関係しない不足は別記し、整理済みの範囲は進める。

### 適用条件と例外

- 小さく、影響範囲が分かっている変更では、既存資料と担当者確認等の相応の確認でよい。全件の大規模研究を要求しない。
- 影響がないと説明できる別機能の設計まで、未確認の役割を理由に停止しない。
- 未提供の任意機能の必要性が未確認なら、確定した目標を守る範囲で保留・延期案を検討できる。

### 原典と解釈の限界

- [Learning about users and their needs](https://www.gov.uk/service-manual/user-research/start-by-learning-user-needs) — Official service-design guidance, not a controlled comparison. No prevalence threshold or automatic feature-removal rule is supplied.
- [Define user needs](https://www.gov.uk/guidance/define-user-needs) — Technology Code of Practice guidance updated 29 October 2026. Role-and-scope feature equivalence is a derived product-design rule, not a direct assertion of this source.

### 確認する反例

- 顧客閲覧は高頻度、支援担当の月次出力は低頻度だが確定要件、追加ダッシュボードは未検証の要望。 → 支援担当の成果と依存を残し、追加要望は仮定として記録する。
- role不明の出力統合と、影響範囲が既知の別画面ラベル修正。 → 統合の判定だけを保留し、ラベル修正は必要な軽量確認で進められる。

## 2. 機能名ではなく、必要な成果と利用条件で置換・統合を照合する

- 統合・置換候補について、元の各role、対象・データ範囲、成果、必要情報、権限、業務条件、アカウント・契約、機器・接続等の関係する条件を、候補先と対応付ける。各条件下で必要な結果を得られる根拠を示し、ラベルの一致を充足の根拠にしない。
- available等の製品表は調査の入口として使う。partialは必要サブタスクが含まれるか確認し、確認済みの必要範囲は採用できる。upcomingは現在提供の証拠にしない。unknown、調査中、非網羅表の未掲載は提供なしとも同等とも断定しない。
- 入口や画面を共有するだけなら、役割・対象範囲・成果の異なる機能を別のまま保持する。同一機能の正本化としてmergeする場合は、既存A03の同一性条件とA02の対応ID・依存を保ち、循環なしで正本のkeepへ解決する。
- 旧部品の名前や方式が変わっても、元の必要成果と利用条件がすべて満たされ、旧部品そのものの維持が必須指定でなければ、旧部品の重複維持を要求しない。機能の正本化、実装手段の置換、異なる機能の同居を区別し、出力契約に合う表現を親が選ぶ。
- 条件差がある場合は、それが必要成果を変えるか確認する。必要条件を満たす別プラットフォーム等の代替は許されるが、未確認の条件を一致扱いせず、実行可能性はR01-A-U03で確認する。

### 適用条件と例外

- 必要サブタスクが提供範囲内と確認できるpartial候補は、当該範囲で採用できる。
- 同じ必要成果を満たす内蔵化・方式変更では、旧実装部品の保存は自動的な義務にならない。
- 異なる機能でも共通入口・同画面への配置は可能であり、機能の同一性を偽装する必要はない。
- 元の業務・提供範囲が明示的に変更された場合、変更済みの条件で比較できる。R01-A-U03の廃止根拠を残す。

### 原典と解釈の限界

- [Feature comparison between new Outlook and classic Outlook](https://support.microsoft.com/en-us/outlook/getstarted/feature-comparison-between-new-outlook-and-classic-outlook) — これは製品仕様の時点比較であり利用者への因果効果の実験ではない。表は非網羅的と明記され、partialから特定タスクの不能を自動推定できない。仕様更新時は再確認する。

### 確認する反例

- 同じ『export』名で、一方は本人分、他方は組織全体。必要な権限も異なる。 → 単純な同一機能mergeを認めず、差を残した別機能の同居は許す。
- 旧アドインと内蔵機能で、必要role・scope・成果・条件を全件確認済み。旧部品そのものの必須指定なし。 → 旧部品の重複維持を要求せず、成果と追跡を維持する置換案を採用可能とする。
- partial候補で必要タスクXは確認済み、不要タスクYは未対応。別ケースでは必要タスクX自体が未対応。 → 前者はXの範囲で通し、後者は充足と記録しない。
- 非網羅的な製品表に機能Zの行がない。 → Zの状態を未確認とし、非実装の断定をしない。

## 3. 現在の提供と代替の成立条件を保ち、廃止・延期の理由を区別する

- 削除・延期案ごとに、機能が現在どの利用者・条件で提供されているか、未提供の計画なのかを記録する。既存能力の停止・再提供待ちを、新機能の着手延期と同じ影響として扱わない。
- 変更対象の各成果を、確認済み代替で継続する、業務・ニーズ自体が終了した、明示された提供範囲変更で提供を終了する、未解決のいずれかとして説明する。これは分析上の区別であり、新しいdisposition enumを追加する指示ではない。
- 代替を根拠に旧提供を終了する場合、必要role・対象範囲・成果についてR01-A-U02を通し、対象利用者が必要な時点に手元の機器・アカウント・権限・データ・接続条件で利用でき、入口から到達できる根拠を記す。別プラットフォームへの変更だけで却下せず、利用可能性を推測で補わない。
- ロードマップ上の予定は現在の代替へ数えない。将来の切替案を作るなら、必要範囲の提供確認を切替成立の条件として残す。未解決の必須成果や依存がある削除・既存提供の延期は、保持案と影響を残し、完了や改善と記録しない。
- 業務終了の根拠、または明示された提供範囲変更があれば、代替のない廃止も提案できる。後者ではニーズが消えたと偽らず、失う成果・対象者・理由を記録する。既存の確定必須条件を自分で変更して、この例外を作らない。
- 変更される既存入口・別名・直接参照の行先を、後継への案内か明示的な終了案内としてAの計画に残す。保存・送信・移行・リダイレクト・失敗時の振る舞いはB/Cへの依存として示す。任意機能の延期には失われる成果、理由、再検討条件を添える。

### 適用条件と例外

- ニーズ・業務の終了が根拠付きで確認できれば、後継機能がなくても廃止できる。
- 明示的な提供範囲縮小は可能だが、残存ニーズを充足済みと記録しない。確定必須条件の変更が必要なら、その決定を未決のまま採用しない。
- 未提供かつ未契約の任意範囲は、確定必須目標と依存を守って延期できる。
- 対象利用者が利用できる実行可能な代替があり、必要成果・条件が維持されるなら、旧機能や旧経路の恒久保持は要求しない。
- 代替の採用・業務終了・範囲縮小のいずれかが既に入力で決定済みなら、同じ許可を取り直す条件は追加しない。

### 原典と解釈の限界

- [Retiring your service](https://www.gov.uk/service-manual/agile-delivery/retiring-your-service) — Whole-service retirement guidance. Applying its preservation questions to an individual feature is this campaign’s inference. Government-specific notification and domain-retention rules are not transplanted.
- [Define user needs](https://www.gov.uk/guidance/define-user-needs) — Technology Code of Practice guidance updated 29 October 2026. Role-and-scope feature equivalence is a derived product-design rule, not a direct assertion of this source.
- [New app for IOS — Sonos Staff response, May 8 2024](https://en.community.sonos.com/controllers-music-services-228995/new-app-for-ios-6892152) — 1件の本人問い合わせとスタッフ回答。利用率、低頻度、全利用者の損害、原因が機能簡素化だったことは示さない。現状の欠陥とは扱わない。PCを持たない利用者への代替不能は本Skill側の条件付き推論。
- [Release notes — Sonos app updates](https://support.sonos.com/en/article/release-notes-sonos-app-updates) — リリースノートは利用者の成功率や原因分析ではない。本文の2026年部分は判断に使わず、2024年の履歴のみ採用。アプリ版・OSで提供時点は異なる。

### 確認する反例

- mobile-only利用者の必須成果を提供中。代替はPC専用で、PCなし。 → その代替を充足とせず、現提供の保持案と確認課題を残す。
- 別端末の代替が対象者の手元で利用でき、必要範囲・権限・データ・時点・入口を確認済み。旧方式の維持義務なし。 → 旧提供の終了を採用可能とする。
- 代替は来月のロードマップのみ。本日から旧提供を停止する案。 → 現在の代替と数えず、将来切替は提供確認を成立条件として未確定にする。
- 業務終了の確定根拠があるケースと、必要性は残るが提供範囲縮小が明示的に決定済みのケース。 → 両者とも廃止を検討可能。後者は失われる成果を未充足として記録し、ニーズ消滅とは書かない。
- 未提供・未契約のcould機能を延期し、必須成果は他機能で維持される。 → 理由・影響・再検討条件を付けて延期できる。

## 4. 観測の範囲と欠測を保ち、不確実な順位を暫定判断にする

- 利用率・件数・需要を削除や延期の根拠にするとき、何を、どの期間、どの対象者・露出範囲で測り、収集や送信にどの制約があるかを必要な範囲で確認する。生の観測値と、その値から言える利用状況を分ける。
- count=0が記録されていれば観測値0は保持する。その対象者が未露出・対象外・送信停止等である可能性を除けない場合、対象全体の非利用は未確認とする。欠測を0で補わず、分母や収集範囲の不明点を非利用の証拠へ変えない。
- 低頻度やゼロの記録だけで削除を決めず、確定要件、必須依存、失敗影響、期限、支援記録等と併せて判断する。高頻度の観測も、それだけで任意機能を必須へ変える根拠にはしない。
- 必須条件を満たす候補を保った後、任意候補の順位を変え得る仮定だけを確認する。根拠のある幅、または具体的な定性シナリオで比較し、順位が逆転するなら暫定順位、影響、確認できる観察事項と再検討条件を残す。
- 欠測の補完に既存要件・聞き取り・支援記録を使えるなら使い、その出所を区別する。新規Telemetryや大規模調査を自動的に要求せず、無関係な設計は進める。根拠のない数値・重み・十分性閾値を作らない。

### 適用条件と例外

- 収集範囲・露出・期間が適切と確認できるゼロ観測は、その範囲の低利用の証拠として使える。ただし単独で廃止を確定しない。
- 定量化の根拠がなければ、順位を変える具体的条件を定性的に比較してよい。
- 小さなUI選択に完全な経済モデルは不要。対象判断に関係する確認で止める。
- 不確実な任意候補でも、確定必須条件を守り、影響と再検討条件を残せる可逆な延期・順位付けは可能。

### 原典と解釈の限界

- [Measuring the benefits of your service](https://www.gov.uk/service-manual/measuring-success/measuring-service-benefits) — Guidance for service investment and benefits. It does not prescribe a feature ranking formula, a numerical confidence threshold, or measured effectiveness for this Skill.
- [Data Collection — Firefox Source Docs](https://firefox-source-docs.mozilla.org/contributing/data-collection.html) — 任意計測と対象範囲を示す仕様で、偏りの方向や大きさを測った研究ではない。計測対象外・送信停止の集団ではログ非観測を非利用と同一視できないというのは導出である。

### 確認する反例

- 両ケースともcount=0。一方はcoverage=unknown、他方は対象期間・露出・収集範囲を確認済み。 → 0の記録を両方残し、前者の対象全体の利用は未確認、後者は確認した範囲のゼロ観測として区別する。
- 月次の必須出力は低頻度。装飾的な任意機能は高頻度。 → 必須出力と依存を保ち、高頻度だけで任意機能をmandatoryへ変えない。
- 任意候補P/Qの順位が、根拠付きの需要シナリオで逆転する。必須条件は両案で維持可能。 → 暫定順位と逆転条件、確認事項、再検討条件を残す。

## 検査と判断の区別

`plan.json`は新規作成では`schema_version: "1.1"`を使う。具体的な追加フィールドは[入出力契約](plan-contract.md)に従う。旧1.0は互換検査として読み取るが、対象範囲・証拠・既存機能の廃止条件は検査されない。

自動検査はscopeと条件IDの一致、根拠IDの解決、廃止記録の有無を確認する。条件名が同じでも業務上等価とは証明しない。`verified_outcomes`は明示した確認結果の記録であり、文字列を書くだけで製品の動作を証明できない。資料のpartial欄は必要サブタスクの確認で補う。実装、保存・送信・再試行、認可実装、画面の操作性はB/C/Dへ引き渡す。

`scope_change`は未充足になる成果を明示した提供範囲の変更案であり、元の必須要件を消す許可ではない。必須要件が残るならその検査は失敗のままにする。別端末の代替は単独では不合格でないが、その端末を対象者が使えるかが必須条件になる。
