# B-IU-004 — Undoの効果と回復経路

「戻す」の対象、実際に戻せる状態、戻らない影響、成立を確認する証拠を先に決める。
配色やアニメーションで元に戻ったように見えても、業務状態の復元を証明しない。

| 種類 | 必要な判断 | 完了を示す証拠 |
| --- | --- | --- |
| 外部作用のない局所編集 | 完全な前状態または正しい逆操作を持つか | 対象の局所状態が復帰したこと |
| 保存済み資源のrestore | 対象・現在状態・権限。期限や競合がある契約ならその条件 | 契約上の復元結果と対象状態 |
| 完了後の業務補償 | 回復する作用・残存影響・失敗/部分結果・照合手段 | 補償自身の終端結果と回復範囲 |
| 実行中の取消 | B-IU-003へ接続 | 取消要求ではなく対象操作の確定結果 |

1. 自動保存、共同編集、API更新、通知等があるか確認する。これらがある場合、局所snapshotの復帰だけで外部作用が戻ると扱わない。
2. 復元を開始できる対象・条件を契約から決める。期限・版番号が不要な単純ローカル編集に、それらを無条件で追加しない。
3. 期限付きofferなら、実行直前にも期限を判定する。同時更新があるならサーバー等の実際の更新地点で競合を防ぐ。UIで確認した古い値だけでは保証しない。
4. 受付、処理中、結果未確認、部分結果、成功、失敗を必要な範囲で分ける。応答喪失・再操作ではB-IU-001/002へ接続する。
5. 成功を確認しても、宣言した範囲だけを回復済みと伝える。失敗時には、確認できた状態、操作参照、利用可能な次の手段を残す。
6. 開始offerの期限と、開始済み操作の照会期間を分ける。offerが消えたことだけで操作IDや回復経路を消さない。

**例：** archiveの解除であれば「archive状態を戻した」が範囲になる。
先に送った通知、料金、他人の編集まで元に戻ったと表示しない。補償失敗だけから「何も変更されなかった」とも推測しない。

補償処理が元の全状態への復元と一致せず、それ自体が失敗する可能性はAzureの設計パターンが説明している。
これは特定アプリに補償機能があるという保証ではない。
[Azure Compensating Transaction](https://learn.microsoft.com/en-us/azure/architecture/patterns/compensating-transaction)

Cloud Storageは具体的な反例になる。復元は新しい世代を作り、周辺の権限やイベントまで全部元通りになるとは限らない。
一括復元は受付後にも失敗し得る。保持日数、世代形式、料金等は同製品の契約であり、一般UIの定数へ持ち込まない。
[Soft delete](https://docs.cloud.google.com/storage/docs/soft-delete) ·
[Long-running operations](https://docs.cloud.google.com/storage/docs/using-long-running-operations)

使用手順のdelete/cancel説明には他の明示仕様と一致しない箇所が観測されたため、その箇所を採用根拠にしていない。
[対象手順](https://docs.cloud.google.com/storage/docs/use-soft-deleted-objects)の復元受付に関する箇所だけを利用した。

## 試験

U01–U09では実際のfixture資源を観測し、期限到達で要求しない、競合で新状態を上書きしない、受付だけで復元しない、
既存操作を照会できることを確かめる。期限境界`now < validUntil`はこのfixtureの契約であり、他APIの境界を規定しない。
