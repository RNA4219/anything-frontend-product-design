# 操作フローの確認

実際の課題で、各指摘に位置、前提、再現操作、期待と実結果、根拠、影響、修正方法を記す。
好みだけを欠陥にせず、検証できる症状に変換する。

- 目的と対象が同じまま、入口から業務上の完了条件へ到達できるか。
- 送信の前に、変更する対象・内容・重要な影響を判断できるか。
- 受付、結果未確認、確定成功、確定失敗、取消要求を区別しているか。
- 旧値は最後の確認値か、現在の正本か。見せ方が証拠より強い主張になっていないか。
- 二重送信、応答喪失、遅れた結果、再読込でも同じ意図と操作を対応付けられるか。
- 状態照会の失敗が元処理の失敗に置き換わっていないか。
- 取消の対象と効果が説明・送信先・終端表示で一致するか。
- 取消に先行して完了した場合、成果物へアクセスできるか。
- 失敗画面に、入力修正・再確認・別案など実行可能な回復操作があるか。
- 同期完了や簡単な可逆操作に、不要な待機や確認を増やしていないか。
- 実APIの原子性や重複防止をモックやUIの文言だけで証明したと記載していないか。

フローの試験結果と、入力デバイス・フォーカス・読み上げ・視覚表現の試験結果は別に記録する。
後者が未実行なら担当C/Dへ、該当するタスクID・状態ID・再現手順とともに渡す。

- [ ] 結果未確認時の見出し・バッジも旧値を現在の確定値と断定していない。
- [ ] 確認できた終端結果から、取消要求と完了の発生順や原因を推測して表示していない。
- [ ] 分岐変更で非該当になった質問のエラーが、確認や送信を妨げていない。有効な他項目のエラーは残し、再び必要になった質問は再検証する。
