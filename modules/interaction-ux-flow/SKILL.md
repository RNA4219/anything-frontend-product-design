# 操作を完了と回復につなげる

利用者が目的を達成したと確認できる状態から逆算する。配色・書体・余白・構図は
[Art Direction](https://github.com/RNA4219/anything-frontend-art-direction)に渡す。
このSkillは、操作が起こす変化、その成立条件、利用者が次に選べる行動を決める。

## 1. タスクと契約を固定する

既存仕様・画面・APIから次を取り出し、欠落は仮定と確認方法を添える。
関係しない不足を理由に全作業を止めない。

| 入力 | 決めること |
| --- | --- |
| 利用者・目的・開始条件 | どこから始め、何を完了したいか |
| 対象ID・現状・希望内容 | 何を変更し、何を保持するか |
| 成功を示す正本と観測 | 受付、処理終了、業務完了のどれを確認したか |
| 副作用・可逆性・期限・権限 | どの確認、取消、回復が成立するか |
| APIの版・冪等性・状態照会 | 再送、結果確認、中断後の再開の条件 |

実APIがない試作ではモック契約を明記する。UIで旧値を残すことは、サーバーで旧状態が
保持された証拠にならない。業務の原子性や復元を必要とするなら、その契約を受入条件にする。

既存の画面では、代表的な入力で開始から結果の確認まで操作し、どの状態で止まったか、
その時点で何が表示されていたかを記録する。新規フローで判断が分かれる場合は、
類似事例の制作者の説明と同じ版の画面を照合し、今回にも当てはまる条件を記す。

## 2. 状態と判断を作る

正常経路を描いた後、各副作用の直前・直後に失敗と中断を入れる。
すべての状態を無条件に増やさず、そのタスクで起こるものを選ぶ。

| 状態ID | 利用者が分かる事実 | 操作 | 遷移条件 | 保持／変更するデータ | 完了・回復の証拠 |
| --- | --- | --- | --- | --- | --- |
| 安定したID | 確定情報と未確認情報を分ける | 利用者／システムを分ける | 許可条件と競合時の結果 | 入力、対象、操作ID、版 | 応答、照会、観察可能な結果 |

各状態で「今どうなったか」「何を選べるか」「選ぶと何が変わるか」「どこで終わるか」を
具体化する。エラー表示だけで終わらせず、修正・再確認・別案・適切な問い合わせへの経路を作る。

## 3. 条件に合う判断手順を読む

| 症状・判断 | 使う手順 |
| --- | --- |
| タイムアウト、受付後の処理、結果不明、再試行、取消競合 | [非同期処理と取消](references/async-outcomes.md) — B-IU-001〜003 |
| 入力拒否・一部修正・確認から戻る・不要な再入力 | [入力修正と確認](references/forms-and-review.md) — B-IU-005/006 |
| Undo・復元・補償・期限切れ | [回復範囲と成立条件](references/undo-and-compensation.md) — B-IU-004 |
| 中断後の再開、accountや権限の変化、版競合、遅い応答 | [作業の復帰と再判断](references/resume-and-conflict.md) — B-IU-007/008 |
| 実装へ渡す前のフロー確認 | [操作フローの確認](checks/flow-review.md) |
| 画面を離れた後の処理、下書きの保存先、状態の通知 | [状態とイベントの判断条件](references/decisions.md) |

**結果未確認を失敗へ丸めない。** 最後に確認した値と今回の希望値を分け、
現在の状態が分からないと明記する。照会を実行していないなら「確認中」と表示しない。

**同じ操作を回復するのか、新しい処理なのかを区別する。** 未確認の処理を別のIDで
再実行しない。同じIDなら安全という判断にも、対象・内容・有効期間の契約が必要になる。

**取消の対象を明示する。** 「閉じる」「変更処理を取り消す」「予約を取り消す」では
効果が違う。受付だけで取消完了にせず、完了が先行したときも実結果へ到達できるようにする。
完了後のUndoや補償は別の契約として扱う。可逆性が未確認のまま提供しない。

## 4. 実装と試験へ渡す

タスクID、状態ID、利用者／システム操作、遷移条件、保持／更新データ、受入条件IDを渡す。
入力部品、フォーカス、キーボード、読み上げ通知の具体実装はUI Engineering担当と合わせる。
Reactやキャッシュの実装規則は既存Art Directionの関連資料を参照し、業務結果の判断と混同しない。

次を同じ入力で実行し、期待結果・観測結果・副作用回数・未検証範囲を残す。

1. 正常完了と確定前の変更・戻る。
2. 入力拒否、処理拒否、応答喪失、状態照会の失敗。
3. 連打、再読込、期限切れ、遅れた応答、取消と完了の競合。
4. 同期完了、単純な可逆編集など、追加手順が不要な反例。

画面の文言だけで副作用の正しさを判定しない。モック試験はその契約内の証拠であり、
実バックエンドの保証や利用者の理解度を実証したとは扱わない。

[予約変更の共通課題](../../tests/fixtures/booking-change.md)では、[状態表とCLIの操作手順](references/booking-change.md)に沿って競合や応答消失を起こし、再表示時の確定日時を照合できる。比較する版では同じ入力と成功条件を使う。結果は[担当間の受け渡し](../../references/handoff.md)に沿って渡す。非同期処理、入力修正、中断後の再開を個別に試す手順は[実行できる検証の一覧](tests/README.md)にある。

## 返すもの

- 目的・開始条件・観測可能な完了条件と、判断に使った仮定。
- 状態・遷移・操作・保持データの表。既存画面なら欠陥の位置、再現手順、影響、修正案。
- 選んだルールの条件・例外・原典。推論したルールは推論と明記。
- 実行したテスト、実結果、残る依存。未実行の項目を合格と書かない。
