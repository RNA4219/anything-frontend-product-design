# 操作を完了と回復につなげる

利用者が目的を達成したと確認できる状態から逆算し、操作の効果・成立条件・次の選択肢を決める。配色・書体・余白・構図は [Art Direction](https://github.com/RNA4219/anything-frontend-art-direction) に渡す。

1. 既存仕様・画面・APIから、目的と開始条件、対象ID・現状・希望、完了を示す正本、副作用・可逆性・期限・権限、APIの版・冪等性・照会条件を取り出す。欠落は仮定と確認方法を記し、無関係な不足で全作業を止めない。実APIがない試作はモック契約を明記する。業務の原子性や復元が必要なら契約を受入条件にする。
2. 正常経路を描き、副作用の直前・直後の失敗と中断を加える。起こる状態を選び、状態ID、利用者／システム操作、遷移条件、保持・変更データ、完了・回復の証拠を記す。各状態で現状、選べる行動、効果、終了点を示し、修正・再確認・別案・問い合わせへの経路を用意する。
3. 通信、受付、処理終端、業務結果、最後に確認した値を分ける。結果未確認を失敗や旧状態の維持と断定せず、照会していないときは「確認中」と表示しない。未確認の操作を新しいIDで自動再実行しない。取消の対象と確定結果を示し、完了後のUndoや補償は別契約として扱う。
4. 該当する手順を読み、正常・拒否・応答喪失・照会失敗・連打・再読込・期限・遅延・取消競合と、追加手順が不要な反例を同じ入力で試す。期待・観測結果、副作用回数、未検証範囲を残す。画面の文言だけで副作用を判定せず、モックの証拠を実バックエンドや利用者の理解の証明にしない。

既存画面は代表入力で開始から結果確認まで操作し、止まった状態と表示を記録する。新規フローで判断が分かれる場合は、類似事例の制作者の説明と同じ版の画面を照合し、適用条件を記す。

## 引き渡し

目的・開始条件・観測可能な完了条件と仮定、状態表、選んだルールの条件・例外・原典、テスト結果と残る依存を返す。既存画面では欠陥の位置・再現手順・影響・修正案を添える。タスクID、状態ID、操作、遷移条件、保持・更新データ、受入条件IDを実装へ渡す。入力部品、フォーカス、キーボード、読み上げ通知はUI Engineeringと合わせる。ReactやキャッシュはArt Directionの関連資料を参照し、業務結果の判断と混同しない。

[フロー確認](checks/flow-review.md)、[検証一覧](tests/README.md)、[予約変更の共通課題](../../tests/fixtures/booking-change.md)と[操作手順](references/booking-change.md)、[担当間の受け渡し](../../references/handoff.md)を必要に応じて使う。比較する版は同じ入力と成功条件を使う。
