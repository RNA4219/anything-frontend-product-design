# UI実装・デザインシステム

利用者が終える作業と完了を確かめる事実を一文で書き、課題ID、開始データ、対象環境、状態と受入条件を受け取る。既存画面は同じ入力で最後まで試す。未定義の状態は判断を変える条件と仮定を記し、[担当間の受け渡し](../../references/handoff.md)に沿って仕様・実装と照合する。

部品カタログ、既存利用箇所、ブラウザーの要素を調べ、役割・操作・値・状態・フォーカス・通知が合えば再利用し、画面固有の組み立てなら合成する。拡張時は入出力・既定値と互換性を示す。合成で操作が途切れる、状態が欠ける、役割が変わる失敗を再現したら局所実装を検討する。複数用途で検証され既存部品や合成で解けない場合は、共有化の根拠、環境、影響、維持担当と適用外を残す。同じ課題・データ・入力方法・成功条件で候補を比較する。

部品の値・取得元、状態・操作・遷移、保持・更新、フォーカス、表示・通知、受入条件を定める。値・無効状態・送信可否は同じ状態から決め、該当する読み込み、空、保留、競合、結果不明、成功を扱う。アクションはbutton、移動はリンク、短い排他的候補はラベル付きの同名radioを候補とし、関連入力はfieldsetとlegendでまとめる。フォーカス移動と通知、重複送信、競合と結果不明からの復旧、トークン変更の波及は[詳細契約](references/contract.md)で確認する。

次の13件は検証前の設計案（DRAFT）。該当する操作を選び、利用環境で確かめる。

- [候補・タブ・キー操作](references/choices.md)
- [ポインター・表示の動き](references/pointer.md)
- [階層・開閉・入力](references/input.md)

キーボードと該当するポインター操作で課題を完了し、狭幅や長いラベル、対象状態と復旧を試す。入力、環境、観察結果、未確認の組合せを報告する。具体例は[予約変更](references/booking-change.md)、出典は[原典](../../research/ui-engineering-design-system/sources.md)。
