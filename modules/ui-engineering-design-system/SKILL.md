# UI Engineering / Design Systems

画面の操作を、入力条件・DOM・イベント・観測結果の組で実装する。仕様に従うこと、静的検査に通ること、ブラウザで動いたこと、利用者が完了できたことを別々に記録する。

## 入力を揃える

利用課題ID、部品ID、利用者の操作、状態ID、実行可能条件、保持・送信する値、取消結果、対象ブラウザと入力方法、既存ライブラリを確認する。既存実装から確かめられる情報は読み取る。未提示なら影響する判断だけを仮定付きにする。

機能の削除・優先順位・情報構造はA、業務状態遷移・再試行・取消ポリシーはBへ渡す。Cはその条件をDOMと部品へ割り当てる。評価基準とリリース判断はDへ渡す。配色・書体・余白・構図の表現は [Art Direction](https://github.com/RNA4219/anything-frontend-art-direction) を使う。既存ライブラリを理由なく置換しない。

## 既存部品の再利用・合成・新設

1. 部品カタログと既存利用箇所を調べ、名前・役割・操作・値・状態・フォーカス・通知の契約が合う部品を再利用する。表示だけの差は既存バリアントや意味トークンで表せるか確認する。
2. 個々の契約が合い、組み合わせが画面固有なら合成する。拡張では追加する入出力・既定値・既存利用箇所への影響を示す。合成で操作が途切れる、状態が欠ける、役割が変わる場合は失敗を再現して局所実装を検討する。
3. 複数用途で検証した共通の必要があり、既存部品や合成で解けない場合に共有部品化を検討する。対応環境・維持担当・例外・変更影響を記録する。新規案と現行案は同じ課題・データ・入力・成功条件で比べる。[継承した採用根拠](../../research/ui-engineering-design-system/sources.md)

## 実行手順

1. **状態の差を列挙する。** 各部品について通常、利用不可、読取専用、処理中、エラー、完了のうち実際に存在する状態だけを表にする。CSSクラスを業務状態の正本にしない。
2. **意味と担当を決める。** 移動・操作・入力・モーダル性から標準要素を検討する。選んだ要素、type、form owner、イベント担当、標準機構に任せる動作を書く。独自widgetにするなら不足機能と検証責務を書く。
3. **状態を実装する。** [部品とフォーカスの契約](references/component-contracts.md) を読み、状態→属性→全実行入口のガード→値の送信→フォーカスを対応づける。取消や画面復旧を確定処理と混ぜない。
4. **条件を反例にする。** 正常操作だけでなく、利用不可、起動元削除、非モーダル、再表示を試す。対象機能に存在しない状態を無理に追加しない。
5. **検査と実機観測を分ける。** 下記の検査を実行し、ブラウザではpointer、Enter、Space、Tab、Shift+Tab、Escapeと実際の送信値を確認する。失敗した条件は再現手順と一緒に修正する。実行できなかった検査を合格にしない。
6. **受け渡す。** 変更したファイル、部品契約、試作起動方法、観測した結果、未確認条件、元資料を渡す。残るリスクを部品IDと状態IDに結び付ける。

## 状態・通知と既存テーマの接続

関連する入力は `fieldset` と `legend`、排他的な短い候補はラベル付きの同名 `radio` を検討する。候補が一つなら選択という操作自体が必要かをBへ確認する。値・無効状態・送信可否は同じ業務状態から決める。

領域の切替で起点が消える場合は、次の作業に適した見出しなどへ移す。同じ領域で進捗や結果だけが変わる場合は、必要なライブ領域を事前に用意して更新し、フォーカスを保つ。移動先の見出しと通知で同じ内容を重複発話させていないかをATで確認する。エラーには対象・分かった事実・復旧操作を可視テキストで示す。

再試行・競合・結果不明・取消の方針はBとサービスの契約を入力として受け取り、Cは実行入口のガードと画面への対応を実装する。結果不明を成功扱いせず、確定値・希望値・操作ID・版のどれで判定するか未定なら判断を保留する。[継承した予約変更契約](references/booking-change.md) はその具体例であり、サービス側の原子性をUIだけで保証しない。

既存テーマを変更する前に、別名の参照元・利用箇所・面と文字の対・状態への影響を確認する。意味が共通の用途は意味名で共有し、部品固有の判断は部品側に置く。色以外の手掛かり・フォーカス・狭幅を実画面で再確認する。配色や書体自体はArt Directionへ、優先情報と主要操作を添えて渡す。

## トークンの取込とテーマ出力

トークンを取り込む・別名やテーマを変更する・CSSへ変換するときは [型・テーマ・CSS出力の契約](references/token-contracts.md) を読む。入力の方言と対応範囲を宣言し、テーマを合成してから参照を解決する。製品が指定した必須ロールと期待型、生成変数名の衝突、出力先と検証範囲を確認する。グラフ検査の成功から実画面のコントラストやWCAG適合を推定しない。

## 出力契約

狭幅・長文・固定層・小さい操作対象を扱うときは [リフローと実効クリック領域の契約](references/layout-contracts.md) を使う。必要な情報と操作を先に列挙し、例外の適用範囲と実際の到達先を確認する。外接矩形・CSS寸法・スクロールバーの有無だけで合否を決めない。[観測手順](checks/layout-observation-protocol.md)でDOM/視覚/Tab/AT順と実入力を別に記録し、未観測はHOLDにする。[予約レイアウト試作](examples/reflow-targets.html)は未観測の教材で、JSON例の数値はsynthetic入力である。

少なくとも次の表と実装差分を返す。問題のない小変更に大規模な新規設計システムを導入しない。

| 部品 / 状態 | 意図・業務入力 | 要素 / 属性 | イベントとガード | 値 / フォーカス / 通知 | 確認条件 |
| --- | --- | --- | --- | --- | --- |
| 例: confirm / unavailable | 実行不可、理由への到達は必要 | button type=button、aria-disabled=true | 全公開入口を同じ条件で抑止 | 理由は常時表示、Tab順は保持 | pointer/Enter/Spaceでも実行数0 |

機械可読にする場合は [契約例](examples/component-contracts.json) の形式を使う。検査は宣言の矛盾を検出する補助であり、DOM・CSS・イベントとの一致を証明しない。

## 検証

リポジトリルートから実行する。

```sh
python3 modules/ui-engineering-design-system/checks/contracts.py modules/ui-engineering-design-system/examples/component-contracts.json
python3 -m unittest discover -s modules/ui-engineering-design-system/tests -p 'test_*.py' -v
node --test modules/ui-engineering-design-system/tests/test_runtime.mjs
```

[予約部品の試作](examples/booking-controls.html) は架空データで、UI部品の状態を確認する教材である。予約の永続化・競合・通信結果不明の回復を実サービス相当に実装したものではない。共通 `booking-change` 全受入条件の合格と混同しない。

以前の統合から [予約変更の一連の試作](examples/booking-change/index.html)、[部品契約・起動手順](references/booking-change.md)、[過去の実行証跡](../../evidence/ui-engineering-design-system/README.md) を保持している。過去の証跡はそこに記載された版・環境の結果であり、今回追加したダイアログ試作の検証済み証拠ではない。この実行では継承ブラウザ試験を再実行していない。

ブラウザ試験は [browser_contracts.py](tests/browser_contracts.py) と [手動確認](checks/browser-checks.md) を使う。未インストールの依存や起動不能はBLOCKEDとして記録し、スクリーンリーダーの発話をDOMから推定しない。

## 根拠と成熟度

実装判断と出典は `registry/C/skills/`、原典位置と検索の比較は `research/ui-engineering-design-system/`、採否と実行証拠は `campaigns/C/rounds/` にある。RegistryのHOLDは、その条件で実証していないことを表す。一般的なWCAG適合や、他モデル・他製品への効果を保証しない。
