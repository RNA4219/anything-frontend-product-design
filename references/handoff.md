# 担当間の受け渡し

最初に共通の利用課題を一文で書き、役割、利用のきっかけ、対象、開始時の事実、成功時に確認できる事実を添える。あとで結び直せるよう、利用課題と受入条件には短く安定したIDを振る。表やJSONなど担当内で扱いやすい形式を使える。たとえば共通の予約課題には `booking-change`、競合時の受入条件には `booking-change-conflict` を使う。

| 作る担当 | 渡すもの | 次の判断 |
| --- | --- | --- |
| A | 利用課題ID、入口、利用者の語彙、情報の分類、対象を見分ける項目、決定に使った証拠 | Bが入口から成功までの経路を決める |
| B | 利用課題ID、状態ID、利用者・システムの操作、遷移条件、保持・更新されるデータ、確認すべき受入条件ID | Cが操作と状態を部品に割り当てる |
| C | 利用課題ID、部品の識別子、状態・操作の対応、入力方法、表示と通知、試作を動かす方法 | Dが対象の挙動を再現する |
| D | 利用課題IDと受入条件ID、前提、再現手順、期待結果、観察結果、証拠、判定と未確認の範囲 | 変更担当が観察を再現し、同じ条件で修正前後を比較する |

案を比較するときは、課題・データ・成功条件をそろえた上で設計の差を決める。既存画面、競合、再試行、戻る操作、表示幅のうち、対象の機能に影響するものを試す。確認結果には実際に操作した範囲を記録する。分類やラベルの発見可能性は、利用者の課題で観察する。

受け渡しの例として [予約変更の試作課題](../tests/fixtures/booking-change.md) を使える。担当を単独で使う場合は既存の仕様、実装、または依頼内容から判断に必要な情報を取る。
